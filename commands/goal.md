# Goal Command

Управление целью, которая живёт дольше одного ответа.

Агент без цели отвечает на последний вопрос и забывает предыдущий. Цель — это
состояние, к которому агент возвращается, даже если разговор ушёл в сторону:
что именно надо получить, что уже сделано, что блокирует.

## Когда использовать

- Задача длиннее одного шага: переписать модуль, разобрать чужой код, довести фичу.
- Работа с перерывами: закрыл сессию, вернулся через день.
- Несколько подряд идущих просьб, где легко потерять исходную.
- Задача, которую легко объявить готовой раньше времени.

Не нужен для вопросов на один ответ, объяснений и мелочей.

## Команды

### Создать цель

```
/goal <формулировка>
```

Формулировка должна быть проверяемой. Не «сделать лучше», а «свести покрытие
тестами выше 80% и показать отчёт».

Агент фиксирует:
- **Что получить** — результат в терминах, которые можно проверить.
- **Критерий готовности** — как понять, что задача закрыта.
- **Ограничения** — чего делать нельзя (не трогать файлы X, не менять API).

### Проверить состояние

```
/goal
```

Показывает: формулировку, статус, сколько уже сделано, что осталось, есть ли блокер.

### Обновить

```
/goal update <уточнение>
```

Когда выяснилось, что исходная формулировка была неточной. Не создаёт новую
цель, а правит текущую — иначе история теряется.

### Закрыть

```
/goal done
```

Только когда критерий готовности выполнен **и проверен**. Не «код написан»,
а «код написан, запущен, вывод показан».

### Снять блокер

```
/goal blocked <причина>
```

Если одна и та же проблема повторяется третий раз. Задача не бросается молча —
фиксируется, на чём именно застряли.

## Что агент обязан делать с активной целью

1. **Проверять перед каждым ответом** — продвинул ли он задачу.
2. **Не заканчивать на «сделал»** — только результат или конкретный блокер.
3. **Возвращаться к формулировке** после каждого побочного вопроса.
4. **Не объявлять готовым** без проверки: запустить, показать вывод.
5. **Не терять ограничения** — если сказано «не трогать tests/», это не отменяется.

## Критерий готовности: как писать

Плохо: «установка работает».
Хорошо: «`npm run termux:install` доходит до `[6/6]`, в конце выводит
`✓ PTY работает`, повторный запуск не падает».

Плохо: «гайд готов».
Хорошо: «статья опубликована, все команды из неё проверены в CLI,
URL отдаёт HTTP 200».

Разница в том, что второе можно проверить, не спрашивая автора.

## Пример полного цикла

```
User: /goal Собрать форк REA под Android и выложить на GitHub

Agent: Цель зафиксирована.
  Получить: рабочий репозиторий, который собирается на Termux
  Критерий: установка проходит 6 шагов, PTY работает, MCP отдаёт 255 инструментов
  Ограничения: MIT-лицензия upstream сохранена

...работа...

User: /goal
Agent: Цель: форк REA под Android
  Статус: в работе
  Сделано: node-pty собирается под bionic, версия Node расширена
  Осталось: формат конфига OpenCode V2
  Блокер: нет

...работа...

User: /goal done
Agent: Проверяю критерий.
  ✓ установка проходит
  ✓ PTY работает
  ✓ 255 инструментов
  Цель закрыта.
```

## Связь с другими командами

- `/plan` — разбить цель на шаги в начале.
- `/tdd` — когда цель требует тестов.
- `/verify` — проверить критерий готовности перед `/goal done`.
- `/checkpoint` — сохранить состояние, если прерываетесь надолго.

## Чего не делать

- Не ставить цель «разобраться» — нечего проверять.
- Не держать активными три цели сразу: фокус теряется.
- Не закрывать по ощущению — только по проверке.
- Не переформулировать молча: старую версию видно в истории, это полезно.
